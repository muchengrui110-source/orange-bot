# 个人 AI 的分层长期记忆

> 一句话：记忆不是越存越多，是分层放、按权重留、按顺序同步。
> 四层、五档权重、四个维护脚本、一条固定的同步顺序，全部在一台 Windows 单机上跑过。

## 一、单文件记忆会怎么烂掉

大多数人给 AI 的记忆只有一个文件：`MEMORY.md`，或者干脆塞进 system prompt。刚开始够用，几周后开始出五种病。

**越写越臃肿。** 每次「记住这件事」都加一行，没人删。实测到过：一个记忆文件近万字节、十几条，一半是「某件事的完整技术细节」，一半是「这件事的教训」。细节本该待在别处。

**每轮都付一次成本。** 热记忆每轮都要注入，不进检索、不按需加载，字数直接变成每轮固定开销。一个文件装下全世界的代价是每句话都变贵，而真正要紧的三条被埋在一百条里。

**改一处，全乱。** 同一条事实在两处都有正文，改了一处、漏了另一处。漏的那处不报错，只是安静地变成假记忆。两个文件对同一个路径给出两种说法并排躺着，就是这么来的。

**旧事实盖新事实。** 文件按追加顺序长，不按真假长。撞上下文预算时，被挤掉的往往是先写的那几条——重要性由写入顺序决定，这是最荒谬的一种排序。

**结论在，出处没了。** 一次体检：几十份原文，被分区正文引用 **0 份**。语义层的结论全在，证据链全断。

## 二、四层结构

| 层 | 载体 | 什么时候进上下文 | 上限 | 生命周期 |
|---|---|---|---|---|
| ① 热记忆 | `MEMORY.md` / `USER.md`（运行时记忆） | **每轮**自动注入 | 插件硬上限 10 KB / 4 KB；方法自定 4 KB 目标 | 只放 W5 与一句话指针 |
| ② 分区工作区 | 每个主题一个工作区，里面的 `AGENTS.md` | **进哪个区加载哪份** | 一份一个主题的量级 | 正文源在 `D:\记忆\对话存档\_工具\bodies\` |
| ③ 原文存档 | 逐字会话记录 | **按需**，一次读一份 | 不设上限 | 永不删 |
| ④ 机制层 | 权重表、权威源、规则、修正日志、脚本 | 不进上下文 | 维护时才读 | 日志只增不删 |

```
每轮注入 ─ ① 热记忆：身份 / 规矩 / 环境 / 手头事
   │ 不够，或要细节
   ▼
按主题 ── ② 分区工作区：进哪个区读哪份 AGENTS.md
   │ 要原话
   ▼
按需 ──── ③ 原文存档：一份一份读，不整层读

④ 机制层：不进上下文，维护时才用
```

### ① 热记忆：每轮都付钱的那一层

只装四类：**身份与红线、动手规矩、环境底座、手头正在做的事**。按段落写，条目之间用一个分隔符（本项目用单独的 `§` 行），这样读的时候知道哪段是「必须永远成立」、哪段是「这周在弄」。

只收最高一档。其余全部下沉到分区，热记忆里最多留一句「某主题见 NN 区」。指针要放在最容易被想到的位置——留指针意味着只剩「这事归 NN 区管」，前提是你先意识到「这是 NN 区的事」。

硬限制：插件对 `MEMORY.md` 是 10 KB、`USER.md` 是 4 KB、单条 8 KB。超了不丢数据，插件先做容量整理、把条目归档，一个可写空间都没有才退回本地归档。但那已经晚了——**超了说明写多了，不是上限小了。**

### ② 分区工作区：按主题拆

12 个工作区，一个区一个主题。进哪个工作区，它目录里的 `AGENTS.md` 自动加载，别的区不加载。一份分区文件的标准骨架：

```
# NN · 主题名 —— 工作区记忆
> 一句话：这个区管什么、什么时候该翻它

## 通用底座（每个区都一样）
身份 / 说话 / 红线 / 环境 / 动手规矩

## 分区正文（源：bodies\NN_*.md）
一、是什么  二、做过的、踩过的（表格）  三、还没解决  四、相关会话

## 本区怎么用（给 agent）
记忆分几层、怎么搜、跨区怎么办、维护顺序、冲突规则

*自动生成于 <时间> · 源文件 NN_*.md · 由脚本写入*
```

「通用底座」和「正文」分开：底座是全局不变的部分，正文是这一主题的内容，同步脚本只换中间那段。「相关会话」表是语义层到原文层唯一的桥，一行指回一份原文。

12 个主题大致是：身份与人设 / 与某甲的关系 / 与某乙的关系 / 某个桥接工程 / 某个小程序 / 剪辑与演示 / 某个平台运营 / 某件法律事项 / 某个技术方向 / 电脑环境与工具链 / 学业与求职 / 杂项。怎么切不重要，重要的是**每个主题只出现一次**。

### ③ 原文存档：永不删

逐字会话，文件名 `YYYY-MM-DD_HHMM_标题_短哈希.md`，一份一次会话；旁边一份 `index.md` 由脚本扫目录生成。这层是情景记忆，删了就真没了。语义层可以压缩、改写、标 `废`，这层不行。

检索规矩：**一次只读要用的那一份**。别「把存档全读一遍」，那等于把上下文一次性烧掉，出来还是一堆无关内容。

### ④ 机制层：不进上下文的那一层

`_meta` 目录，五个部件：

| 文件 | 干什么 | 谁读 |
|---|---|---|
| `权重表.md` | 五档定义、打分四问、标记语法 | 写入时 |
| `权威源.md` | 哪类事实只有第几区能写正文，别处只写指针 | 写入时 |
| `规则.md` | 写、读、改、淘汰、过期、整理的行为约束 | 维护时 |
| `修正.md` | 每次改动的旧值 / 新值 / 理由 | 改动时 |
| 脚本 | 扫权重、批量补标记、出整理报告、降级死链 | 每周或按需 |

外加 `收件箱\`：脚本报告都写这，看完逐条处理，处理完把报告文件名加 `-done`。

机制层是这套东西和「一个 Markdown 文件」的根本区别——它把「怎么维护记忆」也变成可核对的文件，不靠临场发挥。

## 三、每层的读写规则

| 层 | 谁能写 | 什么时候写 | 上限到了怎么办 |
|---|---|---|---|
| ① 热记忆 | **只能**通过运行时记忆工具；`MEMORY.md` 是投影，手改会在下一次写入时消失 | 出现新的 W5 事实；或下沉后更新指针 | 触发下沉六步 |
| ② 分区 | 改 `bodies\NN_*.md`，再跑同步 | 出现某主题的新事实、新教训、新坑 | 低权重下沉旧事段；整段迁到机制层旧事目录 |
| ③ 原文 | 归档流程追加，不修改 | 每次会话结束 | 不设上限，永不删 |
| ④ 机制层 | 人手动写；脚本只读正文、只写报告 | 每次改动、每周整理 | 日志只增不删 |

四条行为约束，都是被踩过才写下来的：

- **先打权重，再决定放哪层。** 顺序反了就会先写进热记忆，之后再也不会挪。
- **读到就核。** 读到任何一条旧记忆，当场判断还成不成立；不成立立刻改，改完把日期换成今天、状态改 `核`。别记「下次改」，没有下次。
- **改之前先抄日志。** 旧行整行抄进 `修正.md`，写清旧值、新值、理由，再改正文。只改不记等于把历史删了。
- **废不删。** 路径变了、软件删了、结论推翻了，标 `废`、日期写当天，挪到该区末尾旧事段。原文层永不删。

### 热记忆满了：下沉六步

触发条件：超过 4 KB 目标，或超过插件上限的八成。

1. **逐条打分。** 拿五档定义过一遍，每条写清档位和理由。
2. **分处置。** 最高档留、措辞可压；次高档下沉分区、留一句指针；中档直接下沉、不留指针；低档标 `废` 删掉；最低档本来就不该在这。
3. **删之前先核分区。** 一条事实只有一个正文位置。分区里已有完整版，热记忆直接删，连指针都不留——重复本身就是干扰源。
4. **分区没有的，先补再删。** 补的时候顺手打标记。**顺序不能反**：先删后补，中间那一刻记忆就真丢了。
5. **能压就压，别整条删。** 细节挪进分区，热记忆只留一句教训。实测过一条五百字节的事故记录：细节归分区，热记忆留一百二十字节的「改源码只用 read/edit/write」。
6. **记修正日志。** 每条一行，日志行数应等于处置条数。

留下的判据，满足任一条就留：是最高档；两百字节以内且每次都用到；不知道会导致行为出错；是教训而不是事实。验收：降到 4 KB 以下、条数落在 7±2、日志行数对得上、重跑权重扫描看覆盖率没掉。

**分区内部的预算（未落地）**：方案里定过核心段 ≤ 800 字（不许挤，挤爆报错）、当前段 ≤ 3000 字、旧事段 ≤ 2000 字。这一版没做——12 份正文仍按主题分七八节，没改成三段结构，旧事段的独立目录也没建。规则成立，实现待定。

## 四、权重与衰减

| 档 | 名字 | 什么进这一档 | 复核周期 | 放哪 |
|---|---|---|---|---|
| 5 | 根 | 身份、隐私红线、动手规矩、说话风格、权限 | 永不 | 热记忆 + 分区核心段 |
| 4 | 硬 | 环境路径、工具铁律、翻过的车、已定结论 | 180 天 | 分区 |
| 3 | 常 | 项目进度、流程、配置、版本号 | 90 天 | 分区 |
| 2 | 细 | 一次性结论、临时状态、具体参数 | 30 天 | 分区或旧事段 |
| 1 | 屑 | 闲聊、临时、可随时丢 | 14 天 | 不进分区，只留原文 |

门槛是硬的：**低于 2 的不写进分区**。想记就记进原文，别在语义层占地方。

### 打分四问

1. 错了会不会造成实际损失？会，4 档起；不可逆的（删文件、隐私、凭据），5 档。
2. 跟关系、承诺、习惯有关吗？有关，4 档起。
3. 原文里还查得到吗？查得到就**降一档**。
4. 用户明确说过「记住」吗？说了直接 4 档起。

第 3 条是唯一能让分区瘦下来的依据。原文里躺着的东西，不值得占语义层的位置。

### 标记与状态

标记写在条目末尾，固定三段：

```
- 环境底座：Python 走全路径 `<DSH_HOME>\...\python.exe`（3.12）〔W4 核2026-11-02〕
```

| 状态 | 意思 | 什么时候用 |
|---|---|---|
| `新` | 刚写，没核过 | 写入当天 |
| `核` | 核过了，还成立 | 核验之后 |
| `疑` | 有怀疑，待确认 | 读到不对但一时查不了 |
| `废` | 过时了，不再成立 | 路径变了、软件删了、结论推翻了 |

脚本只认 `W数字` + 状态字 + 日期这三段文本，外面包什么括号都行——换排版不用改脚本。

### 权重不衰减，复核周期衰减

权重是写入时定的整数，不随时间掉；会变的是「多久核一次」。核完把日期改掉，档位不动。要改档位得说得出理由，记进修正日志——没有理由就升档，等于自己给自己放水。

**权重不是可信度。** 高权重只说明值得留，不说明内容真。这两件事混在一起，就会出现「因为是 W5 所以一定对」这种最糟的推理。

### 什么时候该降级、该忘

| 情形 | 动作 |
|---|---|
| 到期未核 | 进到期清单，优先核查（W4 180 天、W3 90 天、W2 30 天、W1 14 天） |
| 状态 `疑` | 立刻排到最前，不等到期 |
| 路径变了、软件删了、结论被推翻 | 当场改 `废`，挪旧事段 |
| 原文里已有逐字记录 | 降到 1–2 档，只留一句摘要 |
| 长期没被任何一次检索命中 | 沉到旧事段（**未落地**：自动降档与沉底还没写进脚本） |

说句实话：**现在到期不核没有任何后果**。清单能出，但不核不会自动降档、不会沉底、不会拦写入。这一环在方案里，不在代码里。

## 五、维护流水线

改记忆只有一个入口：分区正文源。其他所有副本都是生成的。

```
改 bodies\NN_*.md
   ├─ build_tables.py    扫 原文\ → 重建 原文\index.md
   ├─ sync_partitions.py bodies\ → 12 个工作区的 AGENTS.md
   └─ sync_mnemon.py     bodies\ → 检索库里的 12 份文档镜像
```

```powershell
python -X utf8 D:\记忆\对话存档\_工具\build_tables.py
python -X utf8 D:\记忆\对话存档\_工具\sync_partitions.py
python -X utf8 D:\记忆\对话存档\_工具\sync_mnemon.py
```

### 为什么顺序不能反

三个脚本是**单向生成**：正文源 → 索引 → 工作区副本 → 检索库镜像。任何一步反过来，都是在生成物上手改，下次同步整段覆盖。

- 先同步再改正文：同步出去的是旧内容，你以为已经生效了。
- 直接改工作区的 `AGENTS.md`：下次同步按「底座 + 正文 + 页脚」重拼，你的改动安静消失。
- 两处都改：出现两个正文，权威源失效，之后每次冲突都得人工判断谁对。

### 三个脚本各自干什么

| 脚本 | 输入 | 输出 | 改了会怎样 |
|---|---|---|---|
| `build_tables.py` | `原文\` 里的文件名 | `原文\index.md`（按日期排的表） | 只重建索引，不碰正文；原文为空就是 0 条 |
| `sync_partitions.py` | `bodies\NN_*.md` | 12 个 `AGENTS.md` 的中间段 | 保留「通用底座」和「本区怎么用」，只换正文，顺手改旧路径、更新页脚时间。改前存 `.bak` |
| `sync_mnemon.py` | `bodies\NN_*.md` | 检索库的 12 份文档 | 保留 YAML 头（id/title/description），只换正文，重算 `content_hash` 与 `updated_at`。改前存 `.bak` |

**幂等。** `build_tables.py` 按文件名排序重建，同样目录出同样的表；`sync_partitions.py` 每次从底座切到「本区怎么用」重拼，正文没变时只差页脚时间；`fix_links.py` 把死链降级成纯文本后不再匹配链接语法，重跑无事发生。幂等的意义是：跑一半失败，修好再跑一遍就行，不用手工回滚——前提是每次真存了 `.bak`。

### 冲突怎么裁

```
当前对话 > 最新分区正文 > 检索库（文档 / 记忆空间） > 旧存档
```

这条优先级不自动执行，靠写的时候判断。发现两处正文打架：以正文源为准，改另一处，并在修正日志记一行「因为 X，改为 Y」。最容易被忽略的是「同一件事在两个分区各有一份」——整理脚本能用 3-gram 相似度扫出跨分区重复，但扫出来只是提示，删哪份还得人判断。

### 定期整理

```powershell
python -X utf8 D:\记忆\_meta\consolidate.py
python -X utf8 D:\记忆\_meta\weight.py due
```

整理脚本只出报告、不动文件，查五样：跨分区重复（3-gram 相似度 ≥ 0.65）、失效路径、同一个键的两个值、死链、各段字数。看完逐条处理，处理完把报告改名加 `-done`。之所以设计成只读，是因为自动合并记忆需要判断，判断错了没法回滚——宁可慢，不要乱。

## 六、检索策略

四层不是四个都必须查，按问题类型选层：

| 问题 | 查哪 | 工具 |
|---|---|---|
| 我是谁、规矩是什么、环境路径 | ① 热记忆（已在上下文里） | 不用查 |
| 某个主题的现状、做过的、踩过的 | ② 分区正文 / 检索库文档镜像 | 文档搜索 |
| 当时原话、具体日期、逐字细节 | ③ 原文（一次一份） | 读文件 |
| 这套记忆怎么维护、规则是什么 | ④ 机制层 | 读文件 |
| 长期事实、实体关系 | 记忆空间 | 记忆召回 |

两处容易混：**文档搜索**只搜项目文档，冷归档默认不搜（要显式带 includeArchived）；**记忆召回**只搜已激活的记忆空间，没激活的空间、没配好的 Provider 都搜不出来。「明明存过，就是搜不到」，九成是搜错了层，不是数据丢了。

**检索要带回执。** 查到就说清查了哪里、命中几条；没查到就明说「我查了这几个地方，没找到」，**不能说「没有」**。查不全和不存在是两回事——一次「记忆里没有」被当成「事实不存在」，后面所有推理都建在错的底座上。

**一次只读要用的那一份。** 分区正文一份几千字，原文一份是一次完整会话。要细节就翻**那一份**，别整层读。整层读的代价是上下文被无关内容填满，真正要用的那句被稀释。跨区同理：先搜文档定位，再只读那一份分区文件；别把一个区的私事带到别处。

## 七、单机落地清单

```
D:\记忆\
├─ _meta\                   机制层：权重表 / 权威源 / 规则 / 修正 + 收件箱\
│                           weight.py  autotag.py  consolidate.py  fix_links.py
├─ 对话存档\
│  ├─ _工具\bodies\NN_*.md  分区正文，唯一要改的地方
│  ├─ _工具\                build_tables.py  sync_partitions.py  sync_mnemon.py
│  ├─ 原文\                 逐字会话 + index.md
│  ├─ 分区\                 正文副本，方便直接翻
│  └─ 配置快照\             某次全量备份
└─ 方案\                    设计文档

<DSH_HOME>\
├─ runtime\MEMORY.md USER.md  热记忆（投影，只能通过工具写）
```

|---|---|
| 热记忆 | ≤ 4 KB，只含最高档与指针 |

这几条里最快看出真假的是修正日志：日志空着，说明这套东西又变回摆设了。

## 八、常见坑

**拿「记忆里没有」当「事实不存在」。** 记忆只覆盖被写下来的那部分。没写、写漏、搜错层、只搜了热记忆没搜检索库，都会得到「没找到」。正确表述是「我查了这几处，没找到」，并把查过哪里说清楚。

**把隐私数据混进可公开的文档层。** 分区正文会被同步进工作区、同步进检索库、可能被导出、可能进 Git，原文层才是逐字档案。可公开的文档里，例子只能是「人名甲」「某天」「某主题」这种占位，不该出现真实姓名、账号、住址、健康状况、关系细节。文档层一旦发出去，撤回不了。

**同步脚本改一半失败，留下不一致。** `sync_partitions.py` 成功、`sync_mnemon.py` 失败，就出现「工作区是新的、检索库是旧的」。这时检索到的每一条都是旧事实，而且不报错。修法：修好重跑，别手改任何一侧，跑完对比 `content_hash` 和页脚时间。

**只备份一处。** 有过一次真实事故：旧存档当时只放在一个本地目录里，被误删，回收站也空了，靠检索库里的文档镜像才恢复出正文；原文层那几十份逐字记录彻底找不回，因为只有一份。备份要跨载体：本地目录 + 检索库镜像 + 全量快照，且至少一份不在同一块盘上。

**手改派生物。** `MEMORY.md` 是投影，手改会在下一次写入时消失；分区 `AGENTS.md` 是生成副本，手改会在下一次同步时被覆盖。派生文件只读不写，改就改源头。

**热记忆反复长胖。** 压缩过一次（从近万字节压到两千多），一周后又长回七千多。原因不是上限小，是写入时没门槛。防线是「写之前先问：这条是不是只在一个区用得上」，而不是「满了再压」。

**权重当可信度。** 五档定的是「值不值得留」，不是「对不对」。高权重条目照样会过期，照样要核。

**死链攒着不清。** 体检出过一次：5 处失效路径 + 5 条死链，全是旧存档根迁移后没跟着改的。链接指向不存在的文件不报错，只会在你需要原话时扑空。降级成纯文本只是止血，正事是把路径改对。

**把维护当成一次性的。** 成本不在搭建，在每周那半小时。不跑整理、不记日志、不核到期，三层结构会退化成三个越来越长的 Markdown 文件——和一开始那个单文件没有区别。
